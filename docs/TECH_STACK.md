# Tech stack

- `backend/`: FastAPI and SQLAlchemy Core. It uses Supabase when `DATABASE_URL` is in its environment, and SQLite otherwise, which is what the tests use. All our tables, and the agent's checkpoints, are in the `undercover` schema on Supabase, with at most 4 connections in each process. The answer key for evaluations (the labelled sets and the handlers' decisions) is in tables of its own, which only the copying and the scoring read. Every API operation has an `operation_id`, a one-line docstring and no optional inputs. Paying a claim is a separate operation that takes the amount. The payout rules are an operation of the backend (`calculate_payout`), which takes the approval limit from `data/company.json`.
- `agent/`: the UnderCover Agent on OpenRouter, in five parts and a service.
  - The dispatcher (`agent/dispatcher.py`) works a dispatch or an evaluation. It is a LangGraph graph with no model: a node lists the claims to work and fans out with one `Send` per claim, and a worker node, with `max_concurrency` set to N, calls the harness function `work_claim(claim_id, run_id)`, the dispatcher's only way into the claim agent. The worker has a `RetryPolicy` for LangChain's `ModelRateLimitError` and `ModelTimeoutError`, and an `error_handler` that leaves a claim in progress when the retries run out. The dispatcher saves no progress of its own.
  - The claim agent is a hand-written LangGraph graph with its own state, nodes and edges. It looks the claim up with its tools, including the payout tool, then a decide node records its decision, a wait node pauses with `interrupt()` when the backend says a claim needs a sign-off, and a pay node pays every approval. Each node has a retry policy, and at most 30 model calls are made. Each attempt at a claim has its own thread, and its model nodes record the tokens and OpenRouter's cost of every call.
  - Progress is saved after every step with LangGraph's synchronous Postgres checkpointer in the `undercover` schema, with `durability="sync"`, or in memory without `DATABASE_URL`. Each claim run gets a saver of its own on the process's one shared pool, so claim agents don't take turns on a lock.
  - The agent's service (`agent/service.py`, port 8002 or `UNDERCOVER_AGENT`) is the agent's entry point. The backend asks it through `backend/agent_service.py` to start dispatches, evaluations and single claims, and tells it after each sign-off. On startup it marks any dispatch or evaluation still running as stopped. `uv run -m agent CLM-1001` works one claim from the command line.
  - Langfuse traces every claim, in one session named after the claim's thread, and tags each claim's trace with its dispatch or evaluation.
  - The improver (`agent/improver.py`) is a LangChain `create_agent` on `openai/gpt-6-luna` at medium reasoning effort, with `parallel_tool_calls` off. Its middleware stops a stopped or overspent round, caps its model calls at 40, pauses with `HumanInTheLoopMiddleware` on `propose_change` and `propose_recipe`, and sends a proposal outside the models allowed back before a handler sees it. Its four tools (`read_results`, `propose_change`, `run_evaluation`, `propose_recipe`) reach the backend through `agent/improver_api.py`, which the claim agent never imports. It saves to its own `PostgresSaver` thread for each round, so a round waiting for approval survives a restart. Its evaluations run the dispatcher in a fresh `contextvars.Context`. Its work goes in one Langfuse session named after the round, and the claims of its evaluations are tagged with the round as well as the run.
  - The agents reach claims, documents and their instructions only through the backend's API. They use `openai/gpt-6-luna` with low reasoning effort by default, or the model in the environment variable `MODEL_NAME` if set, such as `openrouter/free`, with no reasoning effort set.
  - Each process keeps to 4 database connections, and the claim agents in it wait for one rather than fail.
- The configuration (instructions, model and reasoning effort) and the improver's recipe are versioned records in the backend, with diffs by `difflib`. Settings are kept in the database, seeded from `data/company.json` and `data/improvement.json`, and the models allowed come from `data/models.json`.
- The judge (`backend/judge.py`) is Jev, `typesafe/jev-1.13`, called through OpenRouter's Decisions endpoint with the `openrouter` package, in the backend because it holds the handlers' reasons. It is not called when `MODEL_NAME` is set.
- Sign-in: the dashboard uses `@supabase/supabase-js` (`VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`), and the backend checks the access token against the project's public keys with PyJWT.
- `dashboard/`: React, Vite and TypeScript.
- `e2e/`: Playwright tests.
- `data/`: the business data the backend starts from. The agent never sees `data/evals/`, which holds the answer key.

Python 3.12 with uv, all in the root `pyproject.toml`. Node 26. The keys are in `.env`: `OPENROUTER_API_KEY`, `DATABASE_URL` (the Supabase session pooler connection string) and the three `LANGFUSE_` values.
IF any of the software is missing what describe above or anywhere in the other files, if the versions are not the one mentioned here then downlaod and update the mentioned version or latest versions.
